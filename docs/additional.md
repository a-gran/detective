# Дополнительные доработки

Этот документ нужен после того, как базовая версия игры уже работает.
Базовая версия считается готовой, если проект запускается командой:

```bash
python main.py
```

Дополнительные задания делятся между двумя командами.
Есть задачи, которые затрагивают весь проект. Это надо учитывать.
В конце есть финальные задачи. Их нужно делать только после того, как все основные и дополнительные доработки проверены.

## Как работать с дополнительными заданиями

Не нужно пытаться сделать все сразу.
Лучше двигаться маленькими шагами:

- выбрать одну задачу;
- изменить только нужные файлы;
- запустить `python main.py`;
- проверить, что старые действия игры не сломались;
- только потом переходить к следующей задаче.

## Подготовка для AI-заданий

Этот раздел относится ко всем, кто будет запускать задачи с AI.
Для AI-части проекта нужны сторонние модули.
Они указаны в файле `requirements.txt`:

```text
requests
python-dotenv
```

Что делает каждый модуль:

- `requests` нужен, чтобы отправлять HTTP-запросы к AI API;
- `python-dotenv` нужен, чтобы читать API-ключ из файла `.env`.

Установить зависимости можно командой:

```bash
pip install -r requirements.txt
```

Если используется виртуальное окружение, сначала нужно включить его, а уже потом запускать установку.
Что нужно проверить:

- файл `requirements.txt` есть в корне проекта;
- в нем указаны `requests` и `python-dotenv`;
- зависимости установлены именно в то окружение Python, из которого запускается игра;
- AI-функции не падают из-за отсутствующих модулей.

Готово, если:

- `import requests` работает;
- `from dotenv import load_dotenv` работает;
- игра запускается через `python main.py`.

### Регистрация в Groq и API-ключ

Каждому, кто запускает AI-задания, нужно зарегистрироваться на платформе Groq.
После регистрации нужно создать свой API-ключ.
API-ключ нужен, чтобы проект мог отправлять запросы к AI-модели.
Что нужно сделать:

- зарегистрироваться на платформе Groq;
- создать API-ключ в личном кабинете;
- создать в корне проекта файл `.env`;
- добавить в `.env` переменную `GROQ_API_KEY`.

Пример содержимого `.env`:

```text
GROQ_API_KEY=ваш_ключ_от_groq
```

Важно:

- API-ключ нельзя отправлять в общий чат;
- API-ключ нельзя писать прямо в `.py` файлах;
- у каждого ученика должен быть свой ключ;
- файл `.env` не нужно загружать в Git.

## Дополнительные задачи команды 1.

### Задача 1. Общий файл интерфейса и безопасный ввод

В корне проекта уже есть заготовка `ui_helpers.py`.
В ней перечислены функции, которые нужно реализовать.
В проекте во многих файлах повторяются похожие функции:

- функция, которая печатает разделитель;
- функция, которая ждет Enter.

Такие функции не нужно держать копиями в каждом файле. Если понадобится поменять текст паузы или длину разделителя, удобнее сделать это в одном месте.
Еще в проекте нужно собрать в одном месте функции для безопасного ввода.
Сейчас игрок может ввести не то, что ожидает программа.
Например:

- буквы вместо номера;
- пустую строку;
- номер, которого нет в списке;
- лишние пробелы до или после ответа.

Нужно сделать общий безопасный ввод, чтобы игра не падала и не возвращалась неожиданно назад.
В `ui_helpers.py` должны появиться функции для разных типов ввода:

- выбор пункта меню;
- выбор номера из списка;
- ввод обычного текста.

Что нужно сделать:

- открыть файл `ui_helpers.py`;
- найти в проекте повторяющиеся функции `print_separator()` и `wait_for_enter()`;
- перенести их в `ui_helpers.py`;
- добавить в `ui_helpers.py` функции для безопасного выбора пункта, номера и текста;
- в остальных файлах заменить копии этих функций на импорт из `ui_helpers.py`;
- проверить, что экраны игры по-прежнему показывают разделители, ждут Enter и не падают при неправильном вводе.

Файлы, где стоит проверить повторения:

- `menu.py`;
- `game_state.py`;
- `final.py`;
- `case.py`;
- `suspects.py`;
- `clues.py`;
- `interview.py`;
- `hints.py`.

Подсказка: готовые версии этих функций уже есть в проекте. Их не нужно придумывать с нуля, можно аккуратно взять существующую логику.
Что нужно продумать:

- где игрок выбирает пункт из готовых вариантов;
- где игрок выбирает номер из списка;
- где игрок вводит свободный текст;
- какое сообщение показать, если ввод неправильный;
- должна ли программа спрашивать повторно.

Места, которые нужно проверить:

- главное меню;
- выбор сложности;
- меню расследования;
- выбор подозреваемого;
- выбор вопроса;
- финальное объяснение версии игрока.

Готово, если:

- функции в `ui_helpers.py` реализованы;
- одинаковые копии функций убраны из файлов;
- файлы используют импорт из `ui_helpers.py`;
- неправильный ввод не ломает игру;
- при ошибке программа понятно объясняет проблему;
- игрок может попробовать ввести ответ еще раз;
- прямой `input()` остался только в `ui_helpers.py`.

### Задача 2. AI-комментарий финальной версии

Эта задача относится к файлу `final.py`.
После финального обвинения игрок пишет свою версию. Код уже должен сам проверить, правильного ли подозреваемого выбрал игрок.
AI можно использовать только после этой проверки.
Что должен делать AI:

- мягко прокомментировать версию игрока;
- объяснить, насколько версия похожа на правильное решение;
- подсказать, на какие улики стоило обратить внимание.

Что AI не должен делать:

- решать, выиграл игрок или проиграл;
- менять правильного преступника;
- спорить с результатом, который уже посчитал код;
- добавлять новые факты, которых нет в `data.py`.

На что обратить внимание:

- результат победы или поражения должен считать код;
- AI получает уже готовый результат проверки;
- комментарий AI не должен менять состояние игры.

Готово, если:

- финальное обвинение работает без AI-ошибок;
- при правильном выборе игра показывает победу;
- при неправильном выборе игра показывает поражение;
- AI только добавляет комментарий к версии игрока.

## Дополнительные задачи команды 2

### Задача 1. Красивый вывод в консоли

Цель: сделать все экраны игры более удобными для чтения.
Общие правила для всех экранов:

- большие экраны должны начинаться с понятного заголовка;
- списки должны быть удобны для чтения;
- между разными смысловыми блоками должны быть пустые строки;
- текст ввода не должен сливаться с предыдущим списком;
- сообщения об ошибках должны быть понятны игроку.

#### `menu.py`

Цель: сделать первое меню игры понятным и аккуратным.
Нужно проверить:

- хорошо ли видно название игры;
- понятно ли, какие пункты можно выбрать;
- есть ли пустая строка перед вводом;
- не слипается ли меню с предыдущим текстом.

Готово, если игрок сразу понимает, как начать игру, посмотреть правила или выйти.

#### `difficulty.py`

Цель: сделать выбор сложности удобным.
Нужно проверить:

- есть ли заголовок "Выбор сложности";
- видно ли название каждой сложности;
- понятно ли описание каждой сложности;
- ошибка неправильного выбора написана человеческим языком.

Готово, если игрок может выбрать сложность без догадок и игра не ломается при неправильном вводе.

#### `game_state.py`

Цель: сделать главный экран расследования удобным для постоянного использования.
На этом экране игрок часто выбирает действия, поэтому он должен быстро видеть состояние игры.
Нужно проверить:

- видно ли выбранную сложность;
- видно ли количество оставшихся вопросов;
- видно ли количество оставшихся подсказок;
- действия расследования выглядят как аккуратный список;
- ввод действия не сливается со списком.

Готово, если игрок легко понимает, сколько ресурсов осталось и какие действия доступны.

#### `final.py`

Цель: сделать финальный экран понятным и торжественным.
Нужно проверить:

- удобно ли выбирать подозреваемого;
- понятно ли, где нужно написать свою версию;
- результат отделен от остального текста;
- правильное решение легко найти глазами;
- после финала игра не выглядит оборванной.

Готово, если финальное обвинение читается как завершение расследования.

#### `case.py`

Цель: красиво показать завязку детектива.
Нужно проверить:

- название дела видно отдельно;
- описание дела не слипается с другим текстом;
- после описания есть пауза, чтобы игрок успел прочитать;
- текст не выглядит как случайный технический вывод.

Готово, если описание дела выглядит как начало истории.

#### `suspects.py`

Цель: сделать список подозреваемых удобным для сравнения.
Нужно проверить:

- у каждого подозреваемого есть номер;
- имя видно отдельно;
- роль подписана;
- характер подписан;
- алиби подписано;
- между подозреваемыми есть пустая строка.

Готово, если игрок может быстро сравнить подозреваемых между собой.

#### `clues.py`

Цель: сделать улики удобными для чтения.
Нужно проверить:

- есть заголовок "Улики";
- каждая улика имеет номер;
- название улики видно отдельно;
- описание улики не сливается с названием;
- между уликами есть пустые строки.

Готово, если игрок может спокойно прочитать все улики и вернуться к расследованию.

#### `interview.py`

Цель: сделать допрос похожим на отдельную сцену игры.
Нужно проверить:

- сначала игрок выбирает подозреваемого;
- потом видит список доступных вопросов;
- вопрос выбирается понятным вводом;
- ответ подозреваемого выводится отдельным блоком;
- после ответа есть пауза.

Важно: AI-вариативность в допросах уже есть в проекте как пример. В этой задаче нужно улучшать именно внешний вид допроса, а не добавлять AI заново.
Готово, если допрос читается понятно и ответ подозреваемого не смешивается с меню или списком вопросов.

### Задача 2. Выход через `0`

Нужно сделать удобный выход из игры.
Игрок должен иметь возможность ввести `0` в любом месте, где программа ждет ввод.
Эта задача отдана команде 2, потому что выход нужно проверить и подключить в разных файлах проекта.

Это должно работать:

- в главном меню;
- при выборе сложности;
- при выборе действия расследования;
- при выборе подозреваемого;
- при выборе вопроса для допроса;
- при вводе финальной версии;
- на паузе после экранов.

Что нужно сделать:

- открыть готовую заготовку `exit_helpers.py`;
- реализовать функции выхода, которые уже перечислены в `exit_helpers.py`;
- подключить функции выхода в `ui_helpers.py`;
- использовать общую проверку команды выхода из `exit_helpers.py`;
- пройти по файлам, где есть ввод игрока;
- убедиться, что после ввода `0` игра показывает сообщение `До встречи, детектив!`;
- убедиться, что после ввода `0` игра завершается через `SystemExit`.

Почему это лучше делать через общую функцию:

- не придется писать одинаковую проверку во всех файлах;
- поведение выхода будет одинаковым во всей игре;
- если текст выхода нужно изменить, это делается в одном месте.

Готово, если:

- `0` завершает игру из любого места ввода;
- Enter по-прежнему продолжает игру на паузах;
- обычные правильные ответы работают как раньше.

### Задача 3. AI-вариативность в подсказках

Файл: `hints.py`
Цель: сделать подсказки более атмосферными, но не менять правила игры.
Код должен сам выбрать следующую подсказку из `HINTS`.
AI может только переформулировать уже выбранную подсказку.
Что AI может делать:

- менять стиль текста;
- делать подсказку более детективной;
- писать подсказку чуть живее.

Что AI не должен делать:

- выбирать другую подсказку;
- менять смысл подсказки;
- называть преступника напрямую;
- добавлять новые улики;
- добавлять новых персонажей;
- менять количество подсказок.

Готово, если:

- подсказку выбирает код;
- количество подсказок уменьшает код;
- AI только меняет формулировку текста;
- без AI игра все равно не ломается.

## Финальные задачи после всех доработок

Эти задачи нужно делать в самом конце.
Перед ними нужно проверить, что игра запускается через:

```bash
python main.py
```

### Финальная задача 1. Оптимизировать импорты

Нужно проверить все `.py` файлы.
Если из одного файла импортируется несколько переменных или функций, их нужно объединить в один импорт.
Пример из проекта:

```python
from data import GAME_TITLE
from data import MAIN_MENU_ITEMS
from data import RULES_TEXT
```

Лучше сделать так:

```python
from data import GAME_TITLE, MAIN_MENU_ITEMS, RULES_TEXT
```

Что нужно проверить:

- нет ли нескольких импортов подряд из одного и того же файла;
- не пропали ли нужные переменные после объединения;
- игра запускается после изменения импортов.

Готово, если редактор больше не подчеркивает импорты из-за одинаковых источников, а проект работает как раньше.

### Финальная задача 2. Удалить тестовые запуски из файлов

Во многих файлах внизу есть блок:

```python
if __name__ == "__main__":
```

Он был нужен, когда файлы проверялись отдельно.
Когда проект почти готов, игру нужно запускать только через:

```bash
python main.py
```

Что нужно сделать:

- найти тестовые блоки внизу отдельных файлов;
- удалить эти блоки;
- оставить запуск проекта через `main.py`;
- проверить игру после удаления.

Важно: не делайте это слишком рано. Пока функции еще пишутся, отдельные проверки файлов могут быть полезны.
Готово, если:

- игра запускается через `python main.py`;
- в отдельных файлах больше нет тестовых запусков;
- удаление тестов не сломало импорты и функции.

### Финальная задача 3. Удалить учебные комментарии

В начале проекта комментарии помогают понять, что делает каждая строка.
Когда проект готов и проверен, лишние учебные комментарии можно удалить.
Что нужно сделать:

- пройти по `.py` файлам;
- удалить комментарии, которые просто пересказывают очевидный код;
- оставить комментарии там, где есть сложная логика или важное предупреждение;
- не удалять сам код.

Пример комментария, который обычно можно убрать в финальной версии:

```python
# Печатаем название проверки для ученика.
```

Важно: эту задачу нужно делать самой последней.
Готово, если:

- код стал чище;
- важные пояснения остались;
- игра запускается через `python main.py`.

## Общее правило для AI

AI нужен только для вариативности текста.
AI не должен менять:

- правила игры;
- количество вопросов;
- количество подсказок;
- выбранного подозреваемого;
- правильного преступника;
- результат финального обвинения.
